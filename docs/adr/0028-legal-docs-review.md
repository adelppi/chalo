# ADR-0028: 法的文書の見直し漏れを、変更の PR とリリースの二段で防ぐ

- 関連: adr/0019, adr/0025, adr/0014, adr/0006, non-functional.md, Issue #129

## コンテキスト

利用規約・プライバシーポリシー(`docs/legal/`)と App Store のプライバシー申告は、
アプリが「何を取得し、どこへ送り、どの権限を使うか」を利用者と Apple に約束する文書である。
実装がこの約束から外れると、利用者への説明と実態がずれ、審査上も問題になる。

`adr/0019` で文面をコードと同じリポジトリ・PR フローに置き、データの扱いが変わる PR で
文面も直せるようにした。ただ、直すかどうかは PR を書く人の記憶に任されていた。
制定(2026年7月17日)以降、写真ライブラリ・触覚フィードバックなどのライブラリや
Edge Function の変更が入ったが、文面は一度も見直されていない。改定日の欄も無く、
いつの実装に対応する文面なのかが読み取れない。

App Store の申告は App Store Connect に手で入力しており、ポリシーとの対応が
どこにも書かれていない。申告とポリシーのどちらかだけが直る余地がある。

## 決定

### 1. プライバシーポリシーをデータの扱いの正にする

- データの取得・送信先・保持の正は `docs/legal/privacy.html` に置く。
- App Store のプライバシー申告は、ポリシーの節から導く。
  - 申告する各データ種別は、ポリシー「1. 取得する情報」の項(1-1〜1-5)のどれかに対応させる。
  - 申告の「利用目的」はポリシー「3. 利用目的」から、「ユーザーに関連付けるか」
    「トラッキングに使うか」は「4. 第三者提供・外部サービス」「5. データの保管と安全管理」から導く。
  - ポリシー「2. 端末の外に出ない情報」に書いたもの(写真・カレンダー連携・送信前の動作ログ)は
    「収集しない」と申告する根拠になる。
- 対応は両方向で一致させる。ポリシーに無いデータを申告しない。申告から漏れた取得をポリシーに書かない。
- 申告の写しは、どの節から導いたかを添えてリポジトリに置く(置き場所は Issue #131 の
  `docs/release/store-listing.md`)。それまでは App Store Connect の画面が申告の実物。

### 2. 規約・ポリシーは最終改定日と改定履歴を持つ

- 冒頭の行に「制定日」と「最終改定日」を並べ、末尾に「改定履歴」の節を置く。
- 改定日は **main にマージした日**(GitHub Pages で公開される日。`adr/0019`)。
- 中身を変えたら、最終改定日を更新し、改定履歴に「日付 何を変えたか」を1行足す。
  体裁だけの修正(誤字・CSS)は改定に数えない。
- 欄を設けた時点(Issue #129)では中身を変えていないため、最終改定日は制定日と同じにする。

### 3. 一段目: 変更の PR で直す

PR テンプレート(`.github/pull_request_template.md`)に「外部への送信・外部サービス・権限を
変えたか」のチェック欄を置く。変えたなら、ポリシー・規約・申告の写しを**同じ PR** で直す。
App Store Connect 上の申告は、その版を提出する前に更新する。

### 4. 二段目: リリースで漏れを拾う

`npm run release:legal-check`(`app/scripts/release-legal-check.js`)が、直近の
`vX.Y.Z` タグ(`adr/0025`)から HEAD までの変更のうち、法的文書に響きうるものを
Markdown で一覧にする。

| 対象 | 拾うもの |
|---|---|
| `app/package.json` の dependencies | 追加・削除したパッケージ。版だけの変更は件数のみ(候補に数えない) |
| `app/app.json` | plugins の追加・削除・オプション変更、`ios.infoPlist` のキー、plugin の権限オプション(`xxxPermission`)の文言 |
| `app/supabase/migrations/`・`app/supabase/functions/` | 追加・変更・削除したファイル(テストを除く) |
| `app/src/`・`app/supabase/functions/` の外部 URL | 増えた・減った URL(`legalLinks` を含む。テストを除く) |

- 差分の判定は I/O を持たない純粋関数(`app/scripts/legal-impact.js`)に切り出し、
  Jest でテストする(`adr/0014`)。git を読むのはランナーだけ。
- 候補が出ても失敗にはしない(終了コード 0)。候補が送信・権限に関わるかは人が判断する。
- `/release` はこのスクリプトを実行し、バンプ PR の本文に
  「**法的文書: 更新した(PR 番号)**」か「**法的文書: 変更なし(理由)**」を必ず書く。

### 5. 送信が増える変更は、配信より先に文面を公開する

規約・ポリシーは main へのマージで即公開される(`adr/0019`)。一方、アプリの変更が
利用者に届くのはストア配信か OTA 配信(`adr/0006`)のとき。

- 外部への送信・外部サービス・権限が**増える**変更は、文面の改定が main にマージされ
  公開されてから配信する。機能の PR と同じ PR で文面を直せば、マージの時点で文面が先に出る。
- 文面の改定を後追いの PR に分けた場合、その PR のマージ前に配信しない。
  main にマージされていないブランチから OTA を配信しない。
- App Store の申告も、その版を審査に出す前に更新する。

## 結果

- 良い点
  - 見直しの機会が「変更の PR」と「リリース」の2回になり、片方で漏れてももう片方で拾える。
  - 申告をポリシーの節から導くため、申告とポリシーが別々にずれていくことがない。
  - 改定日と改定履歴で、どの時点の実装に対応する文面かを利用者も開発者も読み取れる。
  - 判定が純粋関数なので、検出の範囲をテストで確かめながら広げられる。
- 留意点
  - スクリプトは**候補を出すだけ**で、送信が増えたかの判断は人に残る。表示の変更だけの
    ライブラリ(触覚・画像表示など)も候補に出る。
  - 見るのは列挙したファイルだけ。`app/app.config.ts` で plugins や infoPlist を注入する、
    既存のライブラリで新しい送信先へ通信する(URL を変数で組み立てる)といった変更は拾えない。
    このため一段目(PR のチェック欄)を主とし、スクリプトは補助とする。
  - 版だけの依存更新は件数しか出さない。SDK 更新で既存ライブラリの送信内容が変わる可能性は、
    リリースノートを読んで人が判断する。
  - 見るのはコミット済みの内容だけ。作業ツリーの未コミットの変更は対象外。

## 検討した代替案

- **PR テンプレートのチェック欄だけにする**: 書く人の記憶に任せる点は今と変わらず、
  チェックを外したまま通る。リリース時の機械的な拾い上げを足す。
- **候補があればスクリプトを失敗させ、リリースを止める**: 触覚フィードバックのように
  データの扱いに関係しない追加でも毎回止まり、理由を書いて通す形骸化した運用になる。
  候補を出して判断を PR に書かせるほうが、判断の記録が残る。
- **CI(GitHub Actions)で PR ごとに検出する**: 一段目を機械化できるが、いまリポジトリに
  CI は無い(`adr/0025`)。CI を入れるときに同じ純粋関数を流用できる。
- **App Store の申告を正にし、ポリシーを申告から書く**: 申告の分類は Apple の定めた粒度で、
  送信先(外部サービス)や保持期間・削除を表せない。利用者向けの説明として網羅的なのは
  ポリシーのほう。
- **改定履歴を git の履歴に任せる**: 利用者は git を読まない。公開ページ上で改定の有無と
  時期が分かる必要がある。
