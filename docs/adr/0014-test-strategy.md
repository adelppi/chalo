# ADR-0014: テスト戦略

- 関連: adr/0001, adr/0006, adr/0025, non-functional.md

## コンテキスト

AI駆動開発で実装が速く動く分、回帰を機械的に検知したい。一方で iOS シミュレータ越しの重いテストを増やすと反復が鈍る。ロジックの単体検証と、ユーザー体験の通し確認の2層に絞る。

## 決定

採用するテストは次の2つ。

| テスト | 粒度 | ツール |
|---|---|---|
| ロジックテスト | 純粋関数・ユーティリティのみ（副作用なし。日付判定・通知スケジュール計算・タイムゾーン変換・マージなど）。UI・フックは対象外 | Jest（`jest-expo`） |
| E2E テスト | 機能ごとに作成し、各機能で王道のユーザーシナリオを網羅する。正常系・異常系の両方を含める | Maestro |

- **ロジックテストは純粋関数だけ**に絞る。副作用のない関数に切り出せる計算・判定を対象とし、UI 描画やフックは E2E に委ねる。安定して高速、保守コストが低い。
- **E2E は機能単位**で構成する。1機能につき、その機能の王道の使い方を通す正常系と、権限拒否・オフライン・入力不備などの異常系を両方カバーする。フローは `.maestro/<機能名>/` に置き、何を通すか・前提は各フローの先頭コメントに書く（フローの一覧はどこにも持たない）。

### いつ E2E を流すか（`Issue #112` で追加）

| きっかけ | 流す範囲 |
|---|---|
| 画面が変わる変更（新機能・UI に触れる fix） | 変更に関係するフロー。無ければ作る |
| patch リリース | 前回のリリースから変わった機能のフロー |
| **全体リグレッション**：major・minor リリース（バンプ PR の前）／Expo SDK・React Native の更新／Issue で「全体リグレッションが要る」と印を付けた大規模改修 | 全フロー＋手動チェックリスト（`.maestro/README.md`） |

- ロジックだけ・docs だけの変更では流さない（Jest で足りる）。
- **流したフローは録画する**。`maestro record --local <flow.yaml> .maestro/recordings/<name>.mp4` で動画をローカルに保存し、テスト失敗時や見た目の確認に使う。動画はコミットしない（`.gitignore` 対象）。
- PR 本文には、流したフローとその成否・動画のファイル名を書く。全体リグレッションでは、全フローと手動チェックリストの結果を表にしてその PR（リリースならバンプ PR）に書く。
- 全体リグレッションで Maestro から流せない項目（壊す操作・2アカウントが要る操作・外部認証・OS の通知 UI）は、手動チェックリストで人が確認する。

## testID 命名規則

E2E（Maestro）の要素特定には `testID`（iOS の accessibility identifier）を使う。表示文言だけに頼ると、文言調整のたびにフローが壊れる。

- 形式：`<screen>-<element>`（すべて小文字・ハイフン区切り）。`screen` は画面を表す短い語（例：`sign-in`）、`element` は要素の役割（例：`google-button`）。
- 同名の画面が複数 feature にまたがりうる場合は `<feature>-<screen>-<element>` のように feature 名を先頭に付けて衝突を避ける（例：`auth-sign-in-google-button`）。1 feature に画面が1つしかない、または feature が未確定な暫定画面（例：ホーム）では feature 名を省略してよい（例：`home-screen`）。
- 一覧の行など動的に繰り返す要素は末尾にIDを付ける（例：`plans-list-item-{planId}`）。
- E2E が実際に操作・検証する要素にのみ付ける。装飾目的の要素には付けない。

## フローを書くときの注意（`Issue #112` で追加）

- **Pressable の行は1要素にまとまる**。中のテキストが「ラベル, 値, 進む」のような結合文字列になり、Maestro の `text:` は完全一致の正規表現のため部分では当たらない。行の `id` と部分一致の正規表現（`text: ".*値.*"`）で確認する。
- **実データを書き換えるフローは、入力する値を実行ごとに変える**（`evalScript` で時刻などから作る）。固定値だと前回の実行で既にその値になっていて、保存に失敗しても確認が通ってしまう。
- ネイティブのヘッダーボタンは `testID` を持てないため、`accessibilityLabel` を `text:` で参照する（`adr/0016`）。

## 対象外

- **ペア境界（RLS）の自動テストは持たない**。ペア境界のポリシーはレビューで担保する（`adr/0001`）。
- **クラッシュ／エラー監視（Sentry 等）はスコープ外**。本番での回帰検知は別に扱う（`non-functional.md` の保留事項）。
- **CI での E2E 実行は持たない**。ローカルのシミュレータで流す。

## 結果

- 良い点：純粋ロジックを単体で固めつつ、体験の通しは機能ごとの E2E で押さえる。対象がツールと1対1に対応し、AIに「どこに何を書くか」を指示しやすい。
- 良い点：全体を流すのはリリースなどの節目に絞り、ふだんの PR は関係するフローだけにするので、反復を止めずに回帰を拾える。
- 留意点：純粋関数に切り出せないロジックは E2E 側で担保することになる。ロジックを純粋関数へ寄せる設計を心がける。
- 留意点：機能ごとに正常系・異常系を網羅すると E2E 本数が増え、全体リグレッションの所要時間も伸びる。対象の見直しを継続する。

## 検討した代替案

- **コンポーネントテスト（React Native Testing Library）を挟む**：描画・操作を単体で検証できるが、E2E と守備範囲が重なり保守が二重になる。今回はロジック（純粋関数）と E2E の2層に絞る。
- **E2E を主要な数本に絞る**：軽いが、機能ごとの異常系まで手動 QA に委ねることになる。機能単位での網羅を優先する。
- **全体リグレッションを毎 PR で流す**：回帰は早く見つかるが、全フローの実行に時間がかかり反復が鈍る。節目（リリース・基盤更新・大規模改修）に絞る（`Issue #112`）。
- **動画をリポジトリにコミットする／PR に添付する**：レビューで見やすいが、リポジトリが肥大化する。PR への添付は API から行えず手作業になる。ローカル保存とし、PR にはファイル名を書く（`Issue #112`）。
